# 技術仕様書：スマートフォルダ整理機能 (Smart Folder Organizer) 【ドラフト v0.9】

## 1. プロジェクト概要

本機能は、大量の未整理写真に対し、撮影日時（EXIF）と画像内容解析（ローカルCLIPモデル）を組み合わせ、最適な仕分け先フォルダを提案する。ユーザーの確認・編集を経てから物理移動を行う「提案型ワークフロー」を採用し、誤操作のリスクを最小化しつつ整理の自動化を支援する。
外部の生成AI APIは使用せず、すべてローカル環境内で完結させる。

## 2. システムアーキテクチャ

フロントエンド（UI）、ファイル操作コア（Rust）、解析ロジック（Python）の責務を分離する。配布形態は **段階的** とする。

* **Frontend (Webview):** React（本プロジェクトでは React を使用）。提案結果のプレビュー、リネーム、適用操作、Undo操作のUI。
* **Core (Tauri / Rust):** OSファイルシステム操作（パス一覧の取得※、安全なファイル移動・Undoトランザクション）、ローカル画像のプロトコル変換（`convertFileSrc`）。**別プロセスの Python を Rust が常時起動・監視する構成は必須ではない**（既存の単体 FastAPI プロセスとHTTP連携する場合、その監視は省略できる）。
* **解析レイヤ (Python / FastAPI):** `CLIP` モデルによる画像解析、EXIF抽出・時間グルーピングに必要なメタデータ取得、クラスタリング／ゼロショット分類ロジック。
  * **開発・統合フェーズ:** 既存アプリの Python API（例: `src/api_server.py`）に `organize/suggest` 等のエンドポイントを追加する方式を許容する。
  * **配布フェーズ（任意）:** Sidecar として別実行ファイル（PyInstaller 等）をバンドルし、Tauri から起動する方式も選択肢とする。

※ファイル一覧の「真実のソース」は §7.2 を参照（Rust 走査と既存スキャン／DB の二重実装を避ける）。

## 3. 処理パイプライン（アルゴリズム）

提案生成は以下のステップで実行される。

1. **時間ベースのグルーピング (Temporal Clustering)**  
   全対象ファイルについて、可能なら `EXIF:DateTimeOriginal`（および実装上フォールバックとしてのその他日時タグ）を取得し、**取得できない場合はファイルの `mtime`** を用いる。  
   グループ内の並べ順は **撮影日時相当値の昇順** とする（同一タイムスタンプはパス名など決定的な二次キーで順序固定するとよい）。  
   **隣接（時間順で並べたときに隣り合う）** ファイル同士の時間差が **閾値（既定: 4時間）** を超えるポイントでグループを分割する。  
   ※リポジトリ既存コードでは時間ギャップ既定が別値の場合があるため、**本機能の設定値で統一**すること。
2. **代表画像のサンプリング**  
   計算コスト削減のため、各グループから CLIP 推論用の代表画像を抽出する（最初、中間、最後の最大3枚）。
3. **CLIP ゼロショット分類**  
   事前に定義された `presets.json`（語彙リスト）と代表画像を照合し、類似度スコアを算出する。
4. **命名ロジック**  
   各ラベルのスコアをグループ内で平均化。最高スコアのラベルが **信頼度閾値（既定: 0.25）** を超えた場合、そのラベルをフォルダ名案とする。閾値未満の場合は `未分類_YYYYMMDD` 等とする。  
   **閾値はモデル・前処理・類似度の正規化に依存するため既定は調整前提**とし、設定またはログから校正できるようにする。

## 4. API インターフェース (解析レイヤ)

### `POST /api/organize/suggest`

**入力の分離:** `target_path` は整理対象のルート、`destination_root` は §7.1 に従いファイルを移す**出力先ルート**（フラットなサブフォルダの親）とする。提案生成時点では移動は行わないが、suggest の結果検証やパス衝突チェックに `destination_root` が必要になる場合がある。

**対象ファイル:** アプリ全体のサポート画像拡張子に合わせる（例: `.jpg`, `.jpeg`, `.png`, `.heic`, `.webp` など。**実装時の一覧は製品設定に準拠**）。

**エラー応答（概要）:** モデル未準備、タイムアウト、パス不存在、ファイルロック／読み取り不可などは HTTP ステータスまたは構造化ボディで区別できるようにする（詳細は実装時に OpenAPI 等で固定）。

**Request:**

```json
{
  "target_path": "/Users/user/Pictures/Import",
  "destination_root": "/Users/user/Pictures/Sorted",
  "config": {
    "time_gap_hours": 4,
    "confidence_threshold": 0.25,
    "sample_per_group": 3
  }
}
```

**Response:**

```json
{
  "suggestions": [
    {
      "group_id": "uuid_v4",
      "suggested_name": "ゴルフ",
      "reason": "CLIP_match: 0.82",
      "date_range": { "start": "2024-05-01T10:00:00", "end": "2024-05-01T16:00:00" },
      "items": [
        { "path": "/path/to/img1.jpg", "is_representative": true },
        { "path": "/path/to/img2.jpg", "is_representative": false }
      ]
    }
  ]
}
```

## 5. フロントエンド・UI要件 (Tauri)

- **提案プレビュー画面:** 左ペインにフォルダ案のリスト、右ペインに選択中のグループ内写真プレビュー（Grid）。
- **画像表示:** Tauri の `convertFileSrc` カスタムプロトコルを使用してローカル画像を安全かつ高速にレンダリングする。
- **インタラクション:**
  - フォルダ名のインライン編集（リネーム）。
  - グループ間の写真移動（ドラッグ＆ドロップ）または整理対象からの除外（チェックボックス）。
- **適用 (Apply):**
  - 「確定」ボタン押下時、ファイルの移動予定リストを Rust コアへ送信。
  - 移動処理は Rust 側で `std::fs::rename` を主手段として実行し、進捗を `Event` でフロントに通知。

## 6. 重要機能要件

### 6.1. Undo（やり直し）機能の必須実装

ユーザーの心理的・物理的な安全網として、「直近の1回の適用」を取り消せる Undo 機能を実装する。

- **実装方針:** 適用実行時、Rust コア側で移動したファイルの「元のパス」と「新しいパス」のペアリスト（移動ログ）を保持する。**メモリのみ／ディスク永続の別は製品要件で選択**する（アプリ再起動後も Undo したい場合はディスクまたはユーザーデータ領域への保存と TTL を検討）。
- **実行:** Undo がリクエストされた場合、Rust 側でログを逆順に処理し、可能な範囲で `fs::rename` により元のパスへ戻す。完了後にログを破棄する。
- **クロスボリューム:** `rename` が機構上不可能な場合はコピー＋削除が必要になり、Undo と整合させるコストが増える。**v1 では同一ボリューム（同一ドライブ）のみサポート**とするか、クロスボリューム時は「Undo 不可」と明示するかを仕様で固定する。

## 7. 制約事項・非機能要件

### 7.1. システムの制約（既存フォルダ構造の非サポート）

- エッジケースによるバグを防ぐため、**既存の複雑なサブディレクトリ構造の解析・維持、および既存フォルダへの追加提案は行わない。**
- 提案された写真はすべて、ユーザーが指定した「出力先ルートディレクトリ」の**直下**に新規作成されるフラットなフォルダ（例: `Destination/ゴルフ/`, `Destination/未分類/`）へ移動される仕様とする。
- **同名フォルダが出力先に既に存在する場合:** 次のいずれかを製品仕様として明示する（実装はいずれか一つに統一）。
  - **エラー:** 適用を中止しユーザーに報告する。
  - **連番:** `ゴルフ_2` のようにサフィックスを付与する。
  - **マージ:** 既存フォルダへファイルのみ追加する（衝突時のファイル名処理ルールも別途定義）。

### 7.2. パフォーマンスと配布

- **ファイル一覧の単一ソース:** 「パス一覧」を Rust で取るか、既存のスキャン結果／DB から渡すかを決め、**一覧構築ロジックを二重に実装しない**。数万枚規模では Rust 走査やインデックス済み一覧の再利用が有効な場合がある。
- **推論キャッシュ:** 推論結果（Embedding）は SQLite 等にキャッシュし、同一画像の二回目以降の処理をスキップする。**メインのアプリケーションデータベースとは分離したキャッシュ DB／テーブル**とするかを決め、キャッシュキーにはパスに加え **mtime またはコンテンツハッシュ** 等で無効化できるようにする。
- **モデルの軽量化:** バンドルサイズと推論速度最適化のため、CLIP モデルは PyTorch ではなく `ONNX Runtime` での実行を推奨する（開発時は PyTorch パスを許容してもよい）。

### 7.3. プリセット語彙の外部管理 (`presets.json`)

ユーザーが拡張可能なよう、カテゴリリストは設定ファイル化する。

```json
{
  "labels": [
    {"display": "旅行・観光", "keywords": ["travel", "sightseeing", "landmark"]},
    {"display": "食事", "keywords": ["food", "restaurant", "gourmet"]},
    {"display": "ゴルフ", "keywords": ["golf", "golf course"]}
  ]
}
```
